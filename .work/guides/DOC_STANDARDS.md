# Стандарты проектной документации

## Авторитет и категории

1. `accepted`: принятые пользовательские решения — [ADR](../decisions/README.md) и нормативные v7; им подчиняются остальные.
2. `design-proposal`: проектные варианты, ещё не проверенные реализацией.
3. `reference`: актуальные технические контракты и исследования, применимые при отсутствии противоречий с ADR.
4. `superseded`: старое предложение, заменённое новым решением; ссылку на замену ставить явно.
5. `archived-source`: неизменяемый исходник; историческая роль агента, версия пакета или число не становятся действующим решением сами по себе.

**Проблема старого манифеста:** общая метка `historical-context` на ядре не означает отказ от всего содержимого; она означает необходимость сверять с поздними ADR/v7. По мере реализации уточнять статус каждого раздела, не делать массовое автоматическое повышение до `accepted`.

## Метаданные и трассируемость

Для нового нормативного документа укажите `id`, `status`, `date`, `supersedes`, `dependencies`, `acceptance`, `evidence`. Пример: [ADR template](../templates/ADR.md). Все ссылки — относительные внутри репозитория; внешние источники — с датой и точным URL.

При переносе из большого документа сохраните оригинал; секции должны иметь связь `source_anchor → extracted_path`. Оригинальные HTML-якоря в архиве сохранять. Исторические рекомендации по обязанностям отдельных моделей **не переносить в действующие инструкции**.

## Сводные документы

- [README](../../README.md): короткий обзор.
- [AGENTS](../../AGENTS.md): только обязательные общие правила.
- [START_HERE](START_HERE.md): предметный вход.
- [INDEX](../INDEX.md): полная навигация по фрагментам.
- [MANIFEST](../MANIFEST.json): машиночитаемая карта происхождения.
- [CURRENT_STATE](../CURRENT_STATE.md): последний вручную подтверждённый снимок; HEAD и CI при каждом новом отчёте перепроверять в GitHub.

Не создавать альтернативный канонический файл с теми же правилами без ADR; иначе агенты начинают читать конфликтующие версии.
