# ADR-007 — runtime bootstrap P0-00: renderer, generated content, RNG, RulesHash, GUT

- **Status:** ACCEPTED (решение делегировано команде пользователем, [RUNTIME_BOOTSTRAP_PLAN §1, §3](../development/RUNTIME_BOOTSTRAP_PLAN.md)).
- **Date:** 2026-11-12
- **Scope:** только первый runtime-срез P0-00: `game/project.godot`, генерируемый ContentRegistry, `game/core/` (RNG, RulesHash), установка GUT. Геймплейные сцены, боевое ядро, числовая модель симуляции и production-ассеты этим ADR не утверждаются.
- **Supersedes / superseded by:** ничего не заменяет. Уточняет [ADR-001](ADR-001-stack.md) (стек) и реализует «NOT IMPLEMENTED» часть [ADR-006](ADR-006-content-catalog.md). [DRAFT-CONTRACT-002 §3](../spec/v7/draft-contract-002.md) остаётся проектным предложением — см. раздел c.6.

## Контекст

P0-00 впервые создаёт исполняемый проект Godot 4.7.2. До первой строки симуляции нужно закрепить пять вещей, которые потом дорого менять, потому что от них зависят сохранения, replay и parity Python↔Godot:

1. backend рендера в `project.godot`;
2. формат сгенерированного контента и то, **по каким байтам** считается `content_digest`;
3. RNG симуляции, воспроизводимый бит-в-бит в Python и typed GDScript;
4. состав и кодирование `rules_hash`;
5. способ установки GUT 9.7.1 без vendoring в репозиторий.

Проверенные ограничения (Godot 4.7.2 stable, Windows 11, 2026-11-12; команды — в разделе «Verification»):

- `JSON.parse_string` возвращает **каждое** число как `float` (`typeof == TYPE_FLOAT` для `1`), а `JSON.stringify` печатает `1` как `1.0`. Значение `9007199254740993` приходит как `9007199254740992.0`. Байты Python-сериализации в Godot воспроизвести нельзя.
- Разбор дробных литералов в Godot не является строго корректно округляющим: 49 из 49 разных дробных литералов текущего каталога v7 совпали с Python побитно, но денормал `5e-324` разобран как `0.0`.
- `int` в GDScript — знаковый int64, `>>` арифметический, произведение двух 32-битных значений может выйти за int64. Полагаться на переполнение со знаком нельзя.
- `RandomNumberGenerator` сейчас использует PCG32, но документация называет алгоритм деталью реализации, от которой нельзя зависеть.
- [CURRENT_STATE](../CURRENT_STATE.md) запрещает автоматически переносить в игру SHA256-based RNG из проектных предложений.
- SaveEnvelope ([SAVE-CONTRACT-001](../spec/v7/save-contract-001.md), [CHOICE-SAVE-002](../spec/v7/choice-save-002.md)) хранит для потоков `drops`, `enemy`, `offers`, `stage` пару `{seed, cursor}` — десятичные строки uint64.

## Решение

### a. Renderer: `gl_compatibility`

В `game/project.godot`, секция `[rendering]` (полные имена настроек — `rendering/renderer/rendering_method` и `rendering/renderer/rendering_method.mobile`):

```ini
renderer/rendering_method="gl_compatibility"
renderer/rendering_method.mobile="gl_compatibility"
```

`config/features` содержит `"GL Compatibility"`. Mobile и web не являются целью; `.mobile` выставлен только для того, чтобы ни одна платформа не выбрала другой backend молча.

**Измерение** (локально, editor-бинарь 4.7.2, не exported build; RTX 3060, окно 1280×720, vsync off, 20000 `Sprite2D` 48×48 с альфой, четверть спрайтов сдвигается каждый кадр из GDScript, 600 кадров после прогрева):

| Сценарий | draw calls | `gl_compatibility` avg / p95, мс | `forward_plus` avg / p95, мс |
|---|---:|---:|---:|
| одна текстура (атлас) | 2 | 4.95 / 5.55 | 4.84 / 6.71 |
| 4 текстуры, сгруппированы по порядку отрисовки | 5 | 5.18 / 6.50 | 4.46 / 5.08 |
| 4 текстуры, чередуются (батчи разорваны) | 18979 | 42.42 / 48.43 | 11.97 / 12.97 |

Время до первого кадра: 0.7 с против 0.95 с (первый запуск Vulkan — 3.4 с).

**Вывод из чисел:**

- В батчируемом режиме разница в пределах шума: кадр определяет CPU, а не backend.
- При разорванных батчах один draw call стоит около 2.0 мкс в Compatibility против около 0.4 мкс в Forward+. Это единственный измеренный проигрыш Compatibility, и он устраняется на стороне контента: атласы и группировка по полосам Y уже предписаны [s14](../spec/core/s14.md).
- Аппаратный порог Forward+ (Vulkan / Direct3D 12) контентом не устраняется. В 4.7.2 существует `rendering/rendering_device/fallback_to_opengl3`: проект на Forward+ на машине без Vulkan/D3D12 всё равно запускается в Compatibility. Значит, игра в любом случае обязана корректно и быстро работать в Compatibility — это и есть базовая линия разработки.
- Compatibility — подмножество возможностей: переход Compatibility → Forward+ не теряет контент, обратный переход теряет (2D HDR viewport и 2D MSAA в Compatibility не поддерживаются).
- Документация Godot 4.7 рекомендует Compatibility для 2D-игр и самого широкого парка оборудования.
- `--headless` использует dummy-рендер, поэтому на CI выбор backend не влияет (проверено запуском с `--rendering-method forward_plus --headless`).

**Правила до пересмотра:** presentation не зависит от возможностей, которых нет в Compatibility; число draw calls за кадр — отслеживаемая метрика с P0-01 (ориентир для стресс-сцены — не более 1000, то есть около 2 мс из бюджета рендера 8 мс по [s24](../spec/core/s24.md); это ориентир, не критерий приёмки).

**Что запускает пересмотр** (только поправкой к этому ADR):

1. perf-bench P0-02 на **exported** сборке по сценариям s24: `gl_compatibility` не укладывается в `rendering <= 8 ms p95`, а `forward_plus` на той же машине и сборке лучше по p95 не менее чем на 25%;
2. утверждённое арт-направление требует 2D HDR или 2D MSAA;
3. draw calls стресс-сцены не удаётся удержать атласами и группировкой.

Проверка альтернативы не требует правки проекта: `--rendering-method forward_plus`.

### b. Сгенерированный контент: канонический JSON + typed loader

**Генератор:** [`tools/content/generate_registry.py`](../../tools/content/generate_registry.py) (Python stdlib). Выход — `game/content/generated/registry.json` и `game/content/generated/manifest.json`. Руками эти файлы не редактируются.

**Канонические байты** (политика `hip-canonical-json-v1`), одинаково для обоих файлов:

```python
json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8") + b"\n"
```

Ровно один завершающий `\n`, без BOM, без `\r`. Это **не** RFC 8785: форма чисел определяется `json.dumps` CPython (кратчайший round-trip `repr` для float), ключи сортируются по code point. Определение привязано к Python из [toolchain.lock.json](../tooling/toolchain.lock.json).

**`content_digest`** = SHA-256 (нижний регистр, hex) от **всех байтов файла** `registry.json`, включая завершающий `\n`. Дайджест считается по байтам файла, а не по повторной сериализации: Godot повторить сериализацию Python не может (см. «Контекст»).

**Состав `registry.json`:**

```text
{
  "registry_schema_version": 1,
  "digest_policy": "hip-canonical-json-v1",
  "catalogs": { "<stem исходного файла>": <исходный объект целиком> },
  "index":    { "<stem>": "<имя списка, в котором лежат определения с id>" }
}
```

- Источники — **каждый** `.work/config/v7/*.json`, кроме `localization_context.json`. `translations.csv`, `localization_additions.csv` и контекст перевода в дайджест не входят никогда: **локализация не меняет `content_digest`**. Ключи `name_key` внутри каталогов — часть контента, тексты по этим ключам — нет.
- Исходный объект включается целиком, без вырезания служебных полей (`status`, `notes`, `provenance`). Любая правка включённого файла меняет дайджест; это осознанно консервативно.
- `id` определений уникальны **глобально**, между каталогами тоже.
- Fail-closed при генерации: сначала обязан пройти `scripts/validate_content.py`; дубли ключей JSON, `NaN`/`Infinity`, `schema_version != 2`, дубли `id`, неоднозначный список определений — отказ без записи файлов.

**`manifest.json`:** `schema_version: 1`, `kind: "content-registry-manifest"`, `digest_policy`, `generator`, `registry_file`, `registry_sha256` (равен `content_digest`), `registry_bytes`, `definition_count`, `sources: [{path, sha256}]` — SHA-256 сырых байтов каждого исходного файла, пути POSIX от корня репозитория. Меток времени и абсолютных путей нет: выход — чистая функция источников.

**`.gitattributes`:** после общего `*.json text eol=lf` добавляется

```text
game/content/generated/* -text
```

Общее правило `text eol=lf` заставляет git нормализовать концы строк при коммите: файл с `\r\n` в рабочем дереве молча стал бы другим в индексе, и дайджест на этой машине разошёлся бы с закоммиченным. `-text` запрещает git любую конвертацию: в рабочем дереве Windows и Linux лежат те же байты, что в коммите, а случайный `\r` ловится проверкой, а не маскируется.

**CI:** `python tools/content/generate_registry.py --check` пересобирает оба файла в памяти и падает, если закоммиченные байты отличаются (устаревший или отредактированный руками артефакт).

**Loader в Godot (typed GDScript):**

1. читает **байты** `registry.json` (`FileAccess.get_file_as_bytes`), считает SHA-256 через `HashingContext` и сравнивает с `registry_sha256` и `registry_bytes` из манифеста; несовпадение — отказ загрузки, без fallback;
2. только после этого разбирает JSON, индексирует определения по глобально уникальным ID и делает всё дерево **read-only** (`make_read_only`), чтобы потребители не могли изменить каталог после проверки digest. В P0-00 определения отдаются как неизменяемые `Dictionary`; типизированные классы определений (`ClassDef`, `StageDef`, …) появляются в P0-01 вместе с первым потребителем;
3. целые восстанавливает из `float` (`ContentRegistry.integral`) **только там, где схема поля требует int**: значение конечно, `v == floor(v)`, `abs(v) <= 2^53 − 1` → `int(v)`; генератор отклоняет целые вне ±(2^53 − 1) и нечисловые float (`1e400`); иначе ошибка загрузки. Округления и усечения нет;
4. поля-дроби (множители) остаются `float`. Побитовое равенство их значений с Python парсером в общем случае не гарантируется; в P0-00 симуляция их не потребляет. Числовую модель боевого ядра (fixed-point или float) определяет срез P0-01, до этого дробные поля каталога нельзя использовать в логике, влияющей на replay;
5. значения uint64 (seed, cursor) в JSON передаются только десятичными строками.

`.tres`/custom `Resource` как формат генерации не используется (см. «Отклонённые альтернативы»).

### c. RNG симуляции: `hip-rng-v1`

`rng_policy_id = "hip-rng-v1"`. Генератор **counter-based**: блочная функция Threefry-2x32 с 20 раундами (Salmon и др., SC'11). Состояние потока — ровно `(seed, имя, cursor)`; скрытого состояния нет.

**c.1. Блок** `TF(k0, k1, c0, c1) -> (x0, x1)`, все слова — uint32:

```text
R = [13, 15, 26, 6, 17, 29, 16, 24]
ks = [k0, k1, 0x1BD11BDA xor k0 xor k1]
x0 = (c0 + ks[0]) mod 2^32
x1 = (c1 + ks[1]) mod 2^32
for r in 0..19:
    x0 = (x0 + x1) mod 2^32
    x1 = rotl32(x1, R[r mod 8])
    x1 = x1 xor x0
    if r mod 4 == 3:
        s = r div 4 + 1
        x0 = (x0 + ks[s mod 3]) mod 2^32
        x1 = (x1 + ks[(s + 1) mod 3] + s) mod 2^32
rotl32(x, n) = ((x << n) and 0xFFFFFFFF) or (x >> (32 - n))
```

Только сложение, сдвиги, XOR и маска. Умножений нет вообще, наибольшее промежуточное значение меньше 2^62, поэтому в GDScript достаточно int64 с явной маской `& 0xFFFFFFFF` и вспомогательная `mul32` не нужна. Константа `0x1BD11BDA` в расписании ключа исключает вырожденный ключ: «нулевого состояния», которое нужно обходить, у генератора нет, seed `0` допустим.

**c.2. Поток.** Имя потока — ASCII `[a-z][a-z0-9_]{0,7}` (1–8 байт). Зарегистрированные потоки v1: `drops`, `enemy`, `offers`, `stage`.

```text
n0 = байты имени 0..3, little-endian, недостающие = 0
n1 = байты имени 4..7, little-endian, недостающие = 0
(k0, k1) = TF(seed and 0xFFFFFFFF, seed >> 32, n0, n1)      # ключ потока
```

При фиксированном ключе Threefry — биекция счётчика, поэтому два разных имени при одном seed **не могут** получить одинаковый ключ. Пример: seed `0`, `drops` → `n = (0x706F7264, 0x00000073)`, ключ `(0xD916A3AC, 0x47DC014A)`.

**c.3. `next_u32` и cursor.** `cursor` — число уже выданных слов, оно же индекс следующего слова:

```text
block = cursor >> 1
(x0, x1) = TF(k0, k1, block and 0xFFFFFFFF, block >> 32)
результат = x0, если cursor чётный, иначе x1
cursor = cursor + 1
```

Допустимый диапазон `0 <= cursor <= 2^63 - 1` (положительный int64); при `cursor == 2^63 - 1` вызов завершается ошибкой, а не переполнением. Кэш последнего блока — разрешённая оптимизация, не меняющая результат. Пример: seed `0`, `drops`, первые слова `0xA75F916E, 0x6BCAD1E7, 0xCA69B27C, 0x314448DA`.

**c.4. `below(n)`**, `1 <= n <= 2^32`, равномерно в `[0, n)` — пороговое отбрасывание:

```text
threshold = 2^32 mod n
повторять: v = next_u32(); если v >= threshold — вернуть v mod n
```

Принимается `2^32 - threshold` значений — кратное `n`, поэтому смещения нет. Все операнды меньше 2^33. Отброшенное слово **увеличивает cursor**. `below(1)` тоже потребляет ровно одно слово: правило «каждый вызов сдвигает cursor минимум на 1» не имеет исключений. Пример: seed `0`, `drops`, `below(6)` восемь раз → `4, 5, 0, 2, 3, 2, 0, 3`, cursor `8`.

Вероятностные проверки симуляции формулируются в целых: `below(знаменатель) < числитель`. Получение `float` из RNG в v1 не определено. Взвешенный выбор строится на `below(total)` при `total <= 2^32`.

**c.5. Seed, сохранение и восстановление.** Seed забега — uint64, вне арифметики существует как каноническая десятичная строка (`0` или без ведущих нулей, не больше `18446744073709551615`). В GDScript строка разбирается в два uint32 (`hi`, `lo`) поразрядно: `lo = lo * 10 + d; hi = hi * 10 + (lo >> 32); lo = lo and 0xFFFFFFFF`, отказ при `hi > 0xFFFFFFFF` — все промежуточные значения меньше 2^36.

Сохранение потока — существующая форма SaveEnvelope **без расширения**: `rng_policy.streams.<имя> = {"seed": "<uint64>", "cursor": "<uint64>"}`. Для `hip-rng-v1`:

- seed каждого потока равен seed забега; потоки различаются именем. Другой seed потока, неизвестный или отсутствующий поток, лишнее поле, неканоническая строка, `cursor > 2^63 - 1` — отказ загрузки;
- восстановление — O(1): ключ потока из `(seed, имя)`, затем `cursor`. Перемотки нет, слов состояния нет;
- `(seed, cursor)` является полным состоянием, поэтому требование SAVE-CONTRACT-001 «не пересоздавать отсутствующее состояние RNG угадыванием» выполняется буквально: отсутствующий cursor — отказ, а присутствующий определяет поток однозначно;
- требование CHOICE-SAVE-002 «единственный авторитетный offers cursor в `rng_policy.streams.offers.cursor`, seed драфта равен seed потока `offers`» выполняется без изменений схемы.

Выбор между «перемоткой от seed» и «хранением слов состояния» тем самым снят: первый вариант дал бы время загрузки, пропорциональное cursor, второй — третье поле, которое нужно сверять с `(seed, cursor)`.

Добавление потока не меняет последовательности существующих, но требует поправки к этому ADR и новых golden vectors. Косметический RNG presentation не является потоком `hip-rng-v1` и не влияет на симуляцию ([s13](../spec/core/s13.md)).

**c.6. Отношение к DRAFT-CONTRACT-002.** `hip-rng-v1` **не принимает** SHA-256 counter stream из [DRAFT-CONTRACT-002 §3](../spec/v7/draft-contract-002.md). Это означает:

- предложение остаётся DESIGN PROPOSAL; его Python-оракул и golden-значения описывают только предложение и в игру побитно не переносятся;
- сохраняются его нормативно полезные принципы: отдельный поток `offers`, один авторитетный cursor, учёт отброшенных значений в cursor, отбрасывание вместо остатка, сортировка кандидатов по ID, целые положительные веса;
- меняется сырой блок (32 бита вместо 256) и граница суммы весов: `total <= 2^32` вместо `2^64 - 1`; превышение — ошибка контента, а не усечение;
- run UID и choice UID во вход генератора не входят: разделение даёт пара `(seed, имя потока)`, а конкретный выбор определяется позицией cursor;
- когда драфт будет реализован в игре, ему нужен собственный оракул на `hip-rng-v1` с новыми golden vectors; `rng_policy.id` в SaveEnvelope становится `hip-rng-v1`.

**c.7. Измеренная стоимость** (typed GDScript, Godot 4.7.2 headless, 2·10^6 слов): Threefry-2x32-20 с развёрнутыми раундами — 0.44 мкс на слово (один блок на два слова); xoshiro128** — 0.22 мкс на слово. При 300 словах за тик это около 0.13 мс, то есть около 3% предварительного бюджета симуляции 4 мс из s24. Вариант с циклом и массивами — 1.24 мкс на слово; в `game/core/` раунды разворачиваются.

**Известные ограничения:** это не криптографический генератор и не источник секретов; 64-битные блоки одного потока не повторяются (перестановка), отличимо от идеального источника только на масштабе порядка 2^32 блоков, что на порядки больше забега.

### d. `content_digest` и `rules_hash` в runtime

`content_digest` — см. раздел b: SHA-256 hex байтов `registry.json`.

`rules_hash` = SHA-256 hex (нижний регистр) от прообраза в кодировке `hip-rules-hash-v1`. Прообраз — **не JSON**, а байтовая строка с префиксами длины, которую GDScript собирает в `PackedByteArray` и хеширует `HashingContext`:

```text
F(s)   = U32BE(длина s в байтах) + байты s
U32BE  = 4 байта, big-endian

прообраз =
    ASCII "HEAVENISPREY/RULES-HASH/v1" + 0x00
  + F(sim_schema_version)        # каноническая десятичная запись uint32
  + F(content_digest)            # 64 символа [0-9a-f]
  + F(rng_policy_id)             # "hip-rng-v1"
  + F(stage_id)
  + F(difficulty_id)
  + U32BE(число режимов) + F(mode_id) для каждого режима по возрастанию байтов
  + F(class_id)
  + F(seed)                      # каноническая десятичная запись uint64
```

Порядок полей фиксирован. Правила входа (нарушение — отказ, а не нормализация): ID — ASCII вида `[a-z0-9_]+(\.[a-z0-9_]+)+`; `rng_policy_id` — `[a-z0-9]+(-[a-z0-9]+)*`; дубли режимов запрещены; порядок режимов на входе не важен, сортировка побайтовая (`mode.test_10` раньше `mode.test_9`); пустой список режимов допустим и кодируется как `U32BE(0)`. Все поля v1 — ASCII, поэтому байтовая длина равна числу символов.

`sim_schema_version = 1` для среза P0-00. Изменение порядка фаз тика, семантики команд или числовой модели симуляции обязано увеличить его.

Добавление поля (например, хеш draft policy из CHOICE-SAVE-002, когда драфт появится в игре, или tick policy) — это новая кодировка с новым доменным префиксом (`.../v2`) и новыми golden vectors, а не тихое расширение v1.

## Alternatives rejected

- **`forward_plus` по умолчанию.** Выигрывает только при разорванных батчах (таблица в разделе a) и даёт 2D HDR/MSAA, но поднимает аппаратный порог, а fallback всё равно приводит в Compatibility. Остаётся кандидатом по условиям пересмотра. `mobile` не рассматривался: мобильные платформы не цель.
- **`.tres` / custom `Resource` как сгенерированный формат.** Текст `.tres` пишет движок, его байты не контракт между версиями; дайджест пришлось бы считать по второму представлению, а Python-валидаторам — разбирать формат движка. Это второй источник истины, который ADR-006 запрещает. JSON-байты проверяются одинаково в Python и Godot одной функцией SHA-256.
- **Дайджест по пересериализации в Godot.** Невозможен: `JSON.stringify` печатает `1` как `1.0` и не воспроизводит `repr` float из Python.
- **RFC 8785 (JCS).** Потребовал бы собственной сериализации чисел в Python; выгоды нет, пока сериализует ровно один генератор.
- **`text eol=lf` для сгенерированных файлов.** Нормализует, а значит может скрыть расхождение рабочего дерева и коммита; `-text` строже.
- **`RandomNumberGenerator` движка.** Алгоритм — деталь реализации; Python-оракул зависел бы от версии движка.
- **xoshiro128\*\*** (состояние 4×uint32). Вдвое дешевле на слово, но состояние не выводится из `(seed, cursor)` за O(1). Перемотка: 0.22 мкс на слово → около 4.4 с на поток при 2·10^7 слов позднего забега. Хранение четырёх слов состояния: расширение формы `{seed, cursor}` и третье поле для сверки. Произвольный доступ по cursor в сохранениях и отладке расхождений replay ценнее 0.2 мкс на слово.
- **SHA-256 counter stream (DRAFT-CONTRACT-002).** `HashingContext` на каждое слово на порядки дороже, 256-битный блок избыточен, а перенос прямо запрещён CURRENT_STATE без отдельного решения.
- **Threefry-2x32 с меньшим числом раундов.** 20 раундов — значение по умолчанию эталонной реализации с запасом прочности; стоимость 20 раундов (раздел c.7) не измерена как проблема, поэтому экономить на запасе нет причины.
- **Метод Лемира для `below`.** Требует произведения 32×32 → 64 бита, которое в int64 нужно делить на 16-битные половины; пороговое отбрасывание точно и использует только `%` над значениями меньше 2^33.
- **`rules_hash` поверх JSON.** Упирается в ту же невоспроизводимость сериализации; длино-префиксные поля однозначны и собираются в GDScript побайтно.
- **Vendoring GUT в репозиторий или проверка SHA архива.** Первое раздувает diff и смешивает чужой код с нашим; второе ломается при пересборке архива на стороне GitHub.

## Consequences

- Любое изменение включённого файла `.work/config/v7/*.json` меняет `content_digest` и, через него, `rules_hash`; PR обязан содержать перегенерированные артефакты, иначе CI падает на `--check`. Правка локализации дайджест не меняет.
- Экспорт (P0-02) обязан включать `content/generated/*.json` в сборку как есть; тест exported-сборки проверяет дайджест по байтам из PCK. До P0-02 это NOT RUN.
- `game/core/` получает `hip-rng-v1` и `hip-rules-hash-v1` портированием с Python-эталонов; GUT-тесты читают те же golden vectors, что и Python. Числа в векторах — целые не больше 2^53 − 1 или десятичные строки, поэтому переживают разбор JSON в `float`.
- Изменение любой константы, порядка операций, правила `below`, набора потоков или кодировки прообраза — новая политика (`hip-rng-v2`, `hip-rules-hash-v2`), новые векторы и отказ в загрузке старых сохранений без миграции.
- Дробные множители каталога не участвуют в логике replay до решения о числовой модели в P0-01.
- Суммарный вес взвешенного выбора ограничен 2^32; контент, который это нарушает, должен отклоняться при загрузке.
- Производительность, поведение на Linux и на слабом оборудовании этим ADR **не подтверждены** — только перечисленные ниже локальные измерения.
