# GAME-ARCH-00/01 — эталонные фикстуры без игрового runtime

**Статус:** DESIGN-PROPOSAL. `sample.*` — синтетические архитектурные идентификаторы. Это не новые игровые каталоги, не утверждённый баланс и не физическая реализация предметов.

## Что проверено моделью

- Пять исходных XP-предметов: 14+9+17 в одной точке, 7 в соседней, 5 в иной логической области.
- После объединения три представления предметов; сумма по-прежнему 52.
- Подбор радиусом ноль даёт только 40 XP без доступа к соседней точке и другой области.
- Тестовые затраты опыта на последовательные уровни: 5, 12, 20, 30. Из 40 XP получаем +3 уровня и остаток 3.
- В том же тике происходят ритуальная награда и готовность прорыва: **три повышения уровня, ритуал, прорыв**.
- После пяти последовательных подтверждений `build_revision: 1→6`, игровой тик остаётся прежним.
- Повторные сообщения с одинаковым event UID не начисляют XP второй раз, а несовпадающий payload и перекрывающиеся источники отклоняются.
- Пример **не** проверяет доступность конкретной активной техники: trusted eligible offer tokens подаются извне и должны затем связываться с `DraftService` / `BuildTransaction`.

## Дополнительные проверки UX/взаимосвязей

- [GAME-UX-001](../../spec/v7/game-ux-001-oct-2026.md): ручной отложенный выбор **Bank Levels** с сохранением очереди, мгновенная обязательная пауза при ритуале, невозможность отложить обязательную награду, тесты неначисления поддельного XP и запрет на объединение разных HEALTH/CATALYST.
- [Choice bridge](../../../scripts/validate_choice_bridge_proposal.py): три обычные награды последовательно повышают ранг меча и два раза Power, затем четвёртая ритуальная награда становится допустимой эволюцией. Совпадение ревизий и запрет устаревших карточек проверяются статически.

## Локальная проверка (Python stdlib)

```sh
python scripts/validate_run_loop_proposal.py
python -m unittest discover -s tests -p 'test_run_loop_proposal.py' -v
```

Для полной репозиторной проверки использовать `python scripts/validate_work.py`, `python scripts/validate_content.py`, `python -m unittest discover -s tests -v`. CI на GitHub-hosted Ubuntu и Windows-2022 выполняет эти команды.

## Границы честного утверждения

- При объединении физически **разных** позиций сохранение суммы XP не гарантирует сохранение времени подбора. Эталон разрешает объединение **только в той же точке, области, владельце, типе и политике сбора**.
- В реальном контенте дополнительно понадобятся spawn/expiry tick, текущая магнитизация, блокирующая геометрия и политика владельца, иначе эквивалентность сбора не доказана.
- Поддерживается только XP-событие и две модели других решений (ритуал, прорыв), без самой трансформации навыков.
- Схема уровней в примере — **инкрементальная**, не суммарная; не вводит ограничение уровня в игровой архитектуре.
- `run_uid` указан явно; `event_uid` и `source_uids` имеют разные функции. Второй набор нужен для защиты от двойной выдачи после консолидации.
- Эталонный `commit_choice` повышает ревизию, но **не меняет настоящее содержимое RunBuild**. Это модель границы оркестратора, не транзакционный игровой движок. Отдельный [cross-layer witness](../../../scripts/validate_choice_bridge_proposal.py) связывает очередь с **синтетической** проекцией улучшения ранга и открытия эволюции — но также не создаёт игру.
- Нет симуляции паузы, смерти, столкновений, RNG, сетевой игры или сохранений. Эти вопросы оставлены открытыми, а не объявлены проверенными.
